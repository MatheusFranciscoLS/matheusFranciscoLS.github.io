Vardão Central

The system Vardão Máquinas, an authorized Husqvarna dealer in Limeira, Brazil, uses every day at the counter, in sales, finance and inventory. I started with a parts catalog for the counter, and today it is taking over parts of the store’s old ERP, starting with finance.

The problem

At the counter the customer is standing in front of the clerk. To answer "which part is it and how much", the clerk opened a PDF catalog, found the position in the drawing, checked the price in a spreadsheet, looked for the shelf and wrote the quote by hand. A wrong code becomes a return.

Away from the counter, sales, finance and customers lived in an old ERP, separate from everything else. Knowing how much the store sold this month or which customer had gone quiet meant gathering information from different places.

How it evolved

I started with a parts catalog for the counter and grew it as the store asked for more. The dates come from the repository history.

  1. August 2026Parts catalog and search by code, part and model.
  2. SeptemberCounter quotes, saved on the server.
  3. OctoberA CRM with a deal board. Then Finance and Inventory, with access roles, and the old ERP’s rules reproduced.

What I built

Counter

Search by code, part, model or PNC; the official exploded view with a clickable position; list price and shelf; quotes by PDF and WhatsApp. Keyboard first: the clerk works in a hurry.

Sales

A CRM with a deal board and quick filters, customer ranking, cross-selling, reactivation of quiet customers and the machine price table.

Finance

Sales, purchases and expenses, income statement, cash flow, working capital, ABC analysis and closing the till.

Inventory

Items to order, shortages, shelves and special orders for customers, with the deposit they already paid.

Home by role

Each person opens the system on the home screen for their role, with what matters for their day, and the main button changes with the role: "Lançar venda" (record a sale) or "Novo orçamento" (new quote).

Architecture and engineering

  • Many stores, one database. Every record belongs to a store (a store field across the database schema), and the store comes from the signed-in session, not from the browser.
  • Login and roles. Cookie session with a JWT, renewed while the person is working. There are three roles (Administrator, Mechanic, for counter and sales, and Finance), and the server checks the role on every route. Changing a role or deactivating someone ends the session.
  • Basic protection. Rate limiting, security headers (helmet) and input validation on the API.
  • Background work. Reading PDF catalogs goes through a RabbitMQ queue, with retries. The API does not depend on the queue to serve the counter.
  • Database. PostgreSQL with Prisma: 49 models and 91 versioned migrations.

Replacing the old ERP

The store could not lose a single number in the switch. The rule was simple: the same results as the old ERP, or better.

  • The ERP’s rules, tested. I read the ERP’s code screen by screen and reproduced its rules in Vardão Central: income statement, cash flow, working capital, customer ranking and more. Each rule has automated tests.
  • What was hidden. The review showed the ERP still used an old sales table, with its own rules up to a cut-off date. Without that review, this legacy data would have been missing from the income statement and the reports.
  • Safe import. The importer for the ERP data, ready and tested with fictional data, runs as a dry run first, requires the expected totals before writing, checks the totals after writing and can be undone.
  • Better than the original. On sales installments, the ERP added up to R$ 99.99 for R$ 100 in three payments. Vardão Central counts in whole cents and the remainder goes to the first installment.

Rules the product never breaks

Never guess a code

A typed code returns only the exact code and the manufacturer’s official replacement. The AI only picks from a closed list of parts for the machine.

The customer never gets the code

PDFs, WhatsApp messages and printouts leave without the part code, so the customer cannot price it at another dealer with our number.

Data changes are explicit

Importing prices, inventory or sales shows a report before writing and keeps an undo.

Numbers are numbers

Installments in whole cents and dates in the store’s time zone, locked by tests.

Decisions and what I learned

The green test that lied

A job that deletes quotes older than 1 year had a passing test. In production it never ran: the line that started it sat inside the queue’s retry block. I found it by looking at the database. Now there is a test just for that wiring, proven by undoing the fix and watching the test fail.

"Today" ended yesterday

The server runs in UTC and the store in UTC-3: the "until today" filter cut off before the store’s midnight and the owner could not see the day’s own quotes. Every day calculation now uses the store’s time zone, locked by a test.

Refusing beats being wrong

The PDF catalog reader prefers to refuse a doubtful file, saying why, rather than save a wrong code that would spoil the whole search.

The server next to the database

The database is in São Paulo and the API server was in the United States: every query went there and back, about 210 ms each time. I prepared the everyday screens to be served by a function in São Paulo, next to the database, and left only the heavy work, like PDFs and imports, on the main server. One variable switches it back.

Read the old system, don’t trust memory

When rebuilding finance I did not trust the rules I thought the ERP had. I went to its code, and that is what found what was hidden.

Limits and what is missing

  • Real ERP data. The importer is ready and tested with fictional data. Running it on the real data is the store owner’s decision.
  • Tests. The front-end tests run in seconds and passed on the last run. The back-end and end-to-end tests need a database and a browser and are in the project’s CI pipeline.
  • Screenshots. Prices were hidden, because the price list is store data.
